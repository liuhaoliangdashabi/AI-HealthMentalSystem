## D13 上半场：diary 侧内部统计接口打通（20:30）

**产物（diary-service）**
- `controller/InternalDiaryController`：`@RequestMapping("/internal/diary/stat")` + `@GetMapping("/overview")`，三行转发
- `service/DiaryStatService`：`selectCount(null)` / `selectCount(eq(diaryDate,today))` / `avgMoodAll()` / `dailySince(since)` 四次调用，不再 for 循环原始日记
- `entity/DiaryDailyRow`（建议挪 `DTO/response`）：`diaryDate`/`cnt`/`avgMood`，列别名与字段名一字不差，不依赖驼峰转换
- `DTO/response/DiaryStatDTO`（diary 侧副本，**不带 userIds**）
- `DiaryMapper` 两个 `@Select`：`round(avg(mood_score),1)` 全量；`GROUP BY diary_date WHERE diary_date>=#{since}` 出 30 行

**架构决策（面试可讲）**
- 原 `selectList(null)` 全表捞内存聚合 → 判定为"小表能跑、大表必炸"的债，改为**聚合下推 SQL**。判据：指标与表一一对应后，"复用一次扫描"的前提消失，就该让 DB 算
- `userIds` 从契约里删除：几十万 ID 序列化传输不可行；用户数改走 **Redis HyperLogLog**（两服务已有 `uv:{day}`，30 天活跃 = `PFCOUNT` 多 key 天然并集，误差 0.81%）
- **待办**：`RedisKeys.uv` 要拆成 `uv:diary:{day}` / `uv:consult:{day}`，否则日记/咨询 UV 分不开（HLL 不可逆，历史数据只能从改完起算）
- 全量指标（total/avgMoodScore）才是线性膨胀的软肋 → 解法是汇总表增量维护（`INSERT ... ON DUPLICATE KEY UPDATE cnt=cnt+1`）+ 每日对账，现在不做
- 两份 DTO 是契约常态：跨进程只能靠 JSON 字段名对齐，替代方案是抽 contract 模块（本项目收益盖不住成本）

**踩坑（三个都只在运行时暴露）**
1. `@Select` 字符串拼接少空格 → `as avgMoodfrom emotion_diary`，MySQL 语法错误
2. `DiaryStatDTO.Daily d = new Daily()` 建在 for 外面 → Map 30 个 key 全指向同一对象，各天数字相同（**不报错**，最阴）
3. `private Map<String,Daily> daily;` 未 `= new HashMap<>()` → NPE
4. 小脏：`import ...cglib.core.Local` 垃圾 import；Controller 四个无用 import；`@RequestHeader(HEADER_USER_ID)` 永远 null（`DiaryStatClient` 用裸 `RestClient` 不带身份头）→ 已建议删参数

**验收（真实数据）**
- 库内日记 14 条，分布 10 个日期；`days=500` 返回 10 个 key，count 各异（2/1 混），`avgMoodScore=6.5`，`todayNew=0` ✅
- 注意：`total` 已是 **14**，旧记忆里的 19 作废
- 近 30 天窗口内只有 2026-10-16 一条 → 小窗口下"Daily 复用" bug 完全隐身，必须用 `days=500` 才能暴露
