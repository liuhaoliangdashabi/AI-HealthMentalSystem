## 0. 先想清楚：面试官在听什么

面试官问「你这个项目里 Redis 怎么用的」，**他不是想听你用了几个命令**。他在判断三件事：

| 他在判断 | 他通过什么判断 |
|---|---|
| 你是**选型**还是**跟风** | 你能否说出「为什么是这个数据结构，不是那个」 |
| 你有没有**线上感** | 你踩过的坑是不是真坑（教科书坑一听就假） |
| 你有没有**边界判断力** | 你**主动没做**什么，以及为什么 |

所以整个包装的核心策略是：

> **不讲「我用了 Redis 的 5 种数据结构」，讲「每个场景我都先问一句：这个问题 Redis 到底能给我什么」。**

再补一条：

> **主动说出你没做的三件事**（缓存预热、缓存击穿、收藏功能），并给出「收益不值」的理由。
> 一个说「我什么都做了」的候选人，可信度低于一个说「这三件我没做，因为……」的候选人。

## 2. 30 秒项目介绍（背下来）

> 这是一个面向大学生的心理健康系统。核心是 AI 心理咨询对话，配套情绪日记、情绪分析、知识库。
>
> Redis 这块我做了 13 个场景，但我不太想按「用了哪些数据结构」来讲，因为那样听不出选型。
> 我更想按**问题类型**讲：哪些是「省数据库」、哪些是「省内存」、哪些是「跨请求状态」、
> 哪些是「跨进程通信」。同一个 Redis，这四类问题的解法完全不同。
>
> 比如 UV 统计我用 HyperLogLog 而不是 Set，因为精确去重的内存跟人数成正比，
> 而 HLL 固定 12KB，我用 0.81% 的误差换了三个数量级的内存。
> 反过来「在线人数」我就必须用 ZSet，因为 HLL 答不了「谁还在」这种时间窗口问题。
>
> 坑也踩了不少，最有意思的一个是：**一次滚动升级，新任务被旧实例当毒消息吃掉了。**

**为什么这样开场有效**：第 3 句就把「我在按问题类型思考」这个信号打出去了，面试官会顺着你的框架追问，而不是乱枪打鸟。

## 3. 十三个场景，按「Redis 解决了什么类别的问题」分五类

这张表是整套包装的骨架。**面试时先给这张表，再让他挑一个深挖。**

### A 类 · 省数据库（缓存）

| 场景 | key | 结构 | TTL | 一句话 |
|---|---|---|---|---|
| 知识分类树 | `cache:category:tree` | String(JSON) | 手写缓存 | 全站读多写极少，树形结构每次都要拼 |
| 用户信息 | `user::<id>` | String(JSON) | 30min + random(10min) | **全站最高频 SQL**，鉴权过滤器每请求调一次 |
| 数据看板 | `analytics::overview` | String(JSON) | **60 秒** | 四张表全量拉 JVM 聚合，最贵的一次查询 |
| AI 情绪分析 | `ai:emotion:analysis:<md5>` | String(JSON) | 1 小时 | 结果只跟「对话原文」有关，内容不变就不该重算 |
| 文件秒传 | `file:md5:<md5>` | String | 7 天 | md5 命中就跳过 OSS 上传 |

> **面试点：为什么看板只给 60 秒，用户信息给 30 分钟？**
> 因为「数据能容忍多旧」不一样。用户昵称改完 30 分钟内自己看到旧名字是 bug；
> 看板上的「今日新增用户数」晚 1 分钟没人会投诉，但它是最贵的查询，60 秒能挡掉绝大部分重复计算。
> **一个全局 TTL 套所有缓存，必然「有的太短白回源、有的太长像 bug」。**

### B 类 · 省内存 / 省算力（近似计算）

| 场景 | key | 结构 | 一句话 |
|---|---|---|---|
| 每日 UV | `uv:<date>` | **HyperLogLog** | 精确去重内存跟人数成正比，HLL 固定 12KB |

> **面试点：HLL 的误差是「设计的一部分」，不是缺陷。**
> 实测 30 天误差 0.81%。UV 这个指标本身是给人看趋势的，
> 「昨天 1247 人」和「昨天 1250 人」对业务决策没有任何区别，
> 但为了这 3 个人的精确，要多付几百 MB 内存。

### C 类 · 跨请求状态（进程内存放不下 / 不可靠）

| 场景 | key | 结构 | 一句话 |
|---|---|---|---|
| 登录限流 | `login:try:username:<u>` / `login:try:ip:<ip>` | **ZSet 滑动窗口** | 60 秒内超过 N 次失败就封 |
| 日记防刷 | `diary:user:<uid>` | String(计数) | 5 次/分钟 |
| 日记防重 | `diary:dup:<md5>` | String | 内容指纹，60 秒内同样内容不许再写 |
| 日记补算防重 | `diary:analyze:lock:<id>` | String(`SET NX`) | 60 秒内不许重复投递同一个补算任务 |
| 登出黑名单 | `blacklist:token:<md5>` | String | JWT 无状态，登出必须靠黑名单 |
| 在线人数 | `online:users` | **ZSet** | member=userId，score=最后活跃时间戳 |
| 分布式锁 | `lock:fileCleanup` | String(`SET NX PX`) | 定时清理任务多实例只能跑一个 |
| 每日签到 | `sign:<uid>:<yyyy-MM>` | **Bitmap** | 一个月 31 天只需 **4 字节**（31 bit） |

> **面试点（这个很亮）：限流为什么用 ZSet 而不是计数器？**
> 计数器是**固定窗口**：59 秒时打满 5 次，第 61 秒窗口重置，又能打 5 次 ——
> **2 秒内实际允许了 10 次**。ZSet 是**滑动窗口**：每次 `ZADD now`，
> 先 `ZREMRANGEBYSCORE 0 (now-60000)` 清掉窗口外的，再 `ZCARD` 数一下。
> 永远是「最近 60 秒」而不是「这个整分钟」。代价是每个请求要写一条 member，
> 所以 member 用 `时间戳-UUID` 保证唯一（同一个时间戳多次失败不会互相覆盖）。

### D 类 · 跨进程通信（进程内存靠不住）

| 场景 | key | 结构 | 一句话 |
|---|---|---|---|
| AI 分析任务队列 | `stream:ai:task` | **Stream + 消费者组** | 替换 `@Async`，持久化 + 可重投 + 可观测 |
| 死信队列 | `stream:ai:task:dead` | Stream | 重试超上限的任务人工排查 |

> **面试点：`@Async` 差在哪？**
> 四个硬伤：① 任务在进程内存里，发版就蒸发；② 失败只打 `warn`，无重试；
> ③ 积压不可见，只能猜；④ 多实例各有一份队列，负载分不匀。
> Stream 一次解决四个：持久化、可重投、可观测、多实例分担。

### E 类 · 排序与排行榜

| 场景 | key | 结构 | 一句话 |
|---|---|---|---|
| 热门文章 | `article:hot:<date>` → `article:hot:7d` | **ZSet** | 天级 key 天然表达「7 天窗口」 |
| 浏览量回写 | `article:read:delta:<id>` + `article:read:dirty` | String(INCR) + **Set** | 读一次 `INCR`，定时批量回写 DB |

> **面试点：为什么热榜要用「天级 key + ZUNIONSTORE」，而不是一个 ZSet 加过期？**
> 因为 ZSet **没有「按时间淘汰」的能力**。一个 `article:hot` 一直累加，
> 三个月前的爆款永远压着今天的文章。
> 天级 key 让「时间」变成了 **key 的一部分**：`article:hot:2026-10-19`，
> 8 天 TTL 自动过期，定时 `ZUNIONSTORE article:hot:7d 7 article:hot:<近7天>` 合并。
> **窗口从 7 天改成 14 天，只改一个常量，key 名自动跟着变。**

## 4. 五个必须讲深的场景（四段式）

> 挑 3 个讲深就够，剩下 2 个备用。每个都是「问题—方案—踩坑—收益」。

### 4.1 HyperLogLog 做 UV（最有料，优先讲这个）

**问题**
每日独立访客数，原实现是「把当天所有日记查出来，在 JVM 里用 `HashSet` 去重」。
30 天趋势图 = 查 30 天全表 + 建 30 个 Set。数据量一上来内存直接爆。

**方案**
`PFADD uv:<date> <userId>` 写入，`PFCOUNT` 读取，40 天 TTL。
读取时如果某天 `PFCOUNT` 返回 0，**不能直接当成"没人"**，要回源 DB 补一次，补完写回 Redis。

**踩坑（挑三个讲，其余备用）**

| 坑 | 我当时的错误想法 | 真相 |
|---|---|---|
| `PFCOUNT` 返回 0 | 「这天没人来过」 | **0 是二义的**：可能是真没人，也可能是 key 丢了/过期了。必须再问一次 `EXISTS` |
| 空集合 `PFADD` | 「传空数组应该没事」 | Spring 的 `LettuceHyperLogLogCommands:39` 有 `Assert.notEmpty`；换成无源 `PFMERGE` 还是报错，因为 **Lettuce 的 `RedisCommandBuilder:2296` 也有一道 `notEmpty`** |
| 空天永远建不出 key | 「那就每次查库呗」 | 每次请求都回源 = **缓存穿透**。用**墓碑 key** `uv:empty:<date>` 记住「这天查过，结果是 0」 |
| `TTL uv:2026-10-17` = `-1` | 「`expire` 没生效？」 | `expire` 作用在了**没拼日期的 key** 上，对不存在的 key 返回 `false` 且**不抛异常**。key 只拼一次，`add` 和 `expire` 共用同一个变量 |
| 30 天打了 90 次 Redis 往返 | 「每个 key 都 `EXISTS` 一下最保险」 | `hasKey` 写在 `if` 外面，有数据的天也在问。收回 `if(count==null \|\| count==0L)` 里面，**90 次降到 30 次** |

**收益**
- 内存：几百 MB → **固定 360KB**（30 天 × 12KB）
- 误差：实测 **0.81%**
- 30 天趋势图从「查 30 次全表」变成「30 次 `PFCOUNT` + 1 次范围查询兜底」

**三条能拉高上限的认知**

1. **`0` 是二义的** —— 判据永远是「回源看抛异常 或 `EXISTS=0`」，**永远不看"值是 0"**。
   这个思路可以套到所有缓存：`0`、空列表、空对象都可能是「真的没有」也可能是「没查到」。
2. **造不出「空 HLL」** —— Redis 原生支持 `PFADD` 空参，但 Spring 和 Lettuce **各加了一道 `notEmpty`**。
   结论：用墓碑 key 记住「查过、结果是 0」。这是**缓存空对象**的经典套路，防的是缓存穿透。
3. **Spring Data Redis 是两层门** —— 判断「某个 API 能不能这么用」必须两层都查：
   `spring-data-redis` 的 `*Commands` 是适配层，真正拼命令的是 `lettuce-core` 的 `RedisCommandBuilder`。
   查证顺序：`redis-cli` 测原生 → Spring 源码 → Lettuce 源码。

### 4.2 Redis Stream 做 AI 任务队列（最有深度）

**问题**
AI 对话结束后要跑情绪分析（一次完整模型调用，5~10 秒）。原实现挂 `@Async`，
丢进线程池就完事。问题：发版丢任务、失败无重试、积压不可见、多实例各跑各的。

**方案**
```
生产者  XADD stream:ai:task {type, sessionId}
主循环  @Scheduled(800ms) XREADGROUP GROUP ai-workers work-<UUID> COUNT 10 ... >
兜底    @Scheduled(30s)   XPENDING → XCLAIM 抢回卡住的消息
死信    deliveries >= 3   → XADD stream:ai:task:dead + XACK
```

**踩坑**

| 坑 | 真相 |
|---|---|
| 以为 `XACK` 会删消息 | **不会**。PEL 只是个索引（消息ID / 谁拿走的 / 最后投递时间 / 投了几次），`XACK` 只是把它从索引里划掉。`XLEN` 永远不会因为 ACK 变小 |
| 建组用 `ReadOffset.lastConsumed()` | 那是 `$`，**只读组创建之后的新消息**，建组前的积压会被永久跳过。必须 `from("0")` |
| `BUSYGROUP` 抓不到 | 它在 `getCause()` 里，不在 `getMessage()`。Spring 包了一层 `RedisSystemException`，`getMessage()` 只有 `"Error in execution"` → 每次正常启动都打一条假 error |
| 组名加时间戳「防冲突」 | **灾难**。每次重启产生新组，旧组里没 ACK 的消息变孤儿，永远不会被重投。**组名是逻辑身份永远不变，消费者名才是实例身份** |
| 毒消息和瞬时失败混在一起 | 毒消息（字段缺失、id 不是数字）**必须 ACK 丢弃**，不然永远卡在 PEL；瞬时失败（超时、限流）**不能 ACK**，留给兜底重投。**这两类必须分开判断** |

**收益**
- 发版不再丢任务（消息在 Redis 里，不在堆里）
- 失败自动重投，3 次后进死信，不再静默丢失
- 多实例自动分担（消费者组保证同一条只投给组内一个人）
- 新增 `GET /task-queue` 监控接口，积压/死信一眼可见

**最能加分的一段（滚动升级陷阱）**

> 后来加了第二种任务（日记分析），消息体多了一个 `type` 字段。
> 我本来打算「先起新实例、再停旧实例」做滚动升级，写到一半发现这是**致命的**：
> **旧实例不认识 `DIARY_ANALYSIS`，会把它当毒消息 ACK 丢弃** —— 新任务静默消失，
> 而且因为已经被 ACK 了，PEL 里也找不到，连重投的机会都没有。
>
> 那能不能改成「未知类型不 ACK」？也不行 —— 那样它会一直卡在 PEL，
> 从「丢一条」变成「堵一条」，3 次后进死信，等于换了个地方丢。
>
> 所以结论是：**升级顺序必须是「停旧 → 起新」**，不能滚动。
> 这是个很反直觉的结论 —— 滚动升级通常是「更安全」的做法，但在「消费者不认识新消息类型」这个前提下，它反而更危险。

### 4.3 ZSet 做在线人数（最能体现选型思考）

**问题**
管理端要看「当前在线多少人」。没有现成字段，前端也没有心跳接口。

**方案**
鉴权过滤器里，认证通过后 `ZADD online:users <userId> <当前毫秒时间戳>`。
统计时先 `ZREMRANGEBYSCORE online:users 0 (now-5min)` 清僵尸，再 `ZCARD`。

**踩坑 / 思考**

| 问题 | 答案 |
|---|---|
| 为什么不用 Set？ | **Set 只能回答「谁来过」，回答不了「谁还在」。** 要判断「还在不在」必须按时间过滤，而按分数范围过滤正是 ZSet 的强项 |
| 为什么不复用 UV 的 HLL？ | HLL 只能给一个估算数字，**答不了时间窗口**。而且 HLL 不支持删除单个元素 |
| 心跳放哪？ | 放在**认证之后**。放前面的话，攻击者拿一堆废 token 刷接口，能把在线人数刷上天 |
| 统计失败返回什么？ | **返回 `-1`，不是 `0`。** `0` = 「真的没人」，`-1` = 「我不知道」。混成一个值，监控就会在最需要它的时候撒谎 |

**收益**
- 在线人数从「没有」到「精确到人」
- 僵尸自动清理，不需要额外的定时任务
- 代价：内存跟在线人数成正比（这个是精确统计的必然成本，不像 UV 可以近似）

### 4.4 ZSet 做 7 天滚动热榜

**问题**
知识库「推荐阅读」要按热度排。原实现是 `ORDER BY read_count DESC` ——
**三个月前的爆款永远排第一，今天的文章永远上不来。**

**方案（三层）**

```
写：浏览一次 → INCR article:read:delta:<id> + SADD article:read:dirty <id>
            （同时 ZINCRBY article:hot:<今天> 1 <id>）
刷：定时任务 → 从 dirty 集合取 id → 批量 UPDATE DB → 清 delta
合：定时任务 → ZUNIONSTORE article:hot:7d 7 article:hot:<近7天>，TTL 90 秒
读：先读 article:hot:7d；不足 TOP 用「最新已发布」补齐
```

**踩坑**

| 坑 | 真相 |
|---|---|
| 用一个 ZSet 累加所有浏览 | **ZSet 没有「按时间淘汰」的能力**，三个月前的爆款永远压着新文章。必须让「时间」成为 key 的一部分 |
| 窗口天数写死在 key 里 | `"article:hot:7d"` 和 `ARTICLE_HOT_WINDOW_DAYS=7` 各写一个 7。改成 14 天时 key 还是 `7d`，**名字和内容对不上，排查能绕死人**。改成 `"article:hot:"+DAYS+"d"` |
| 改完编译报 `illegal forward reference` | **`static final` 按书写顺序初始化**，被引用的常量必须写在前面 |
| 榜单不足 TOP 就只返回几条 | 热度榜是「有人读过才进榜」，冷启动时只有 1 条 → 推荐位只有 1 条。修：不足 TOP 用最新已发布补齐 |
| Redis 挂了推荐位整块消失 | 原来 `catch` 直接 `return List.of()`。修：**Redis 异常也走补齐分支**，退化成「按发布时间」而不是「什么都不显示」 |

**收益**
- 推荐位从「1 条」恢复到「6 条」（库里全部已发布文章）
- 热度第一的仍在最前，只是后面补满了
- 浏览量从「每次浏览一次 UPDATE」变成「定时批量 UPDATE」

### 4.5 缓存一致性：`@CacheEvict` 漏了会怎样

**问题**
用户信息是全站最高频 SQL —— 鉴权过滤器每个请求都要调一次 `getUserById`。
加了 `@Cacheable` 之后 QPS 降下来了，但埋了个雷。

**方案**
```java
@Cacheable(cacheNames = "user", key = "#userId")
public UserDetailResponseDTO getUserById(Long userId) { ... }

@CacheEvict(cacheNames = "user", key = "#userId")
public UserDetailResponseDTO updateProfile(...) { ... }

@CacheEvict(cacheNames = "user", key = "#userId")
public String updateAvatar(Long userId, String avatar) { ... }
```

**踩坑**

| 坑 | 真相 |
|---|---|
| 只加 `@Cacheable` 没加 `@CacheEvict` | 改完昵称，**库是新的、接口返回是旧的**。用户以为没保存成功，反复点，反复"失败" |
| 「等 TTL 过期就好了」 | 用户信息 TTL 30 分钟。**30 分钟内他一直看到旧昵称**。查库对、查接口错 —— 因为第三份数据在 Redis |
| 封号场景更严重 | `status` 走缓存的话，**被封的号还能用 30 分钟**。这不是体验问题，是安全问题 |
| 直接缓存 `User` 实体 | 实体里有 `password`（bcrypt 哈希）。进 Redis 等于密码哈希外泄。必须缓存 **DTO** |

**收益**
- 全站最高频 SQL 的 QPS 显著下降
- 写路径一致性由 `@CacheEvict` 保证，不依赖 TTL

**追问预案：为什么不用「先更新库再删缓存」的双写？**
> 因为这里是**同一个方法内**的读改写，`@CacheEvict` 在方法返回后执行，
> 天然满足「库更新成功才删缓存」。方法抛异常时缓存不删（数据也没改），是对的。
> 双写要处理的是「两个系统都写成功」的问题，这里只有一个系统要写，另一个只是删，简单得多。

## 5. 七条反常识认知（拉开差距的地方）

> 这部分是整套包装里最值钱的。**技术细节可以背，认知只能真的踩过才有。**

### ① `0` 是二义的

`PFCOUNT` 返回 0、缓存返回空列表、查询返回 null —— 都可能是「真的没有」，也可能是「没查到」。
**判据不能是「值是 0」，必须是「有没有抛异常 / key 存不存在」。**

### ② 缓存不能做「写路径的准入判断」

缓存是为了「读得快」，不是为了「判断得准」。
缓存会过期、会被淘汰、会丢 —— 拿它判断「这个请求该不该放行」，
一旦缓存没了，判断就失效了。**写路径的判断必须回源数据库。**

### ③ 派生数据失效：不清空比「没有」更误导人

AI 情绪分析是「日记正文的函数」。用户改了正文，旧结论必须**立刻作废**。
留着旧的比显示「无」更糟 —— 用户会以为分析结果仍然有效。
所以编辑日记时：`.set(aiEmotionAnalysis, null)` + 重新投递分析任务。

### ④ 用「值有没有变」推断「任务有没有完成」是不可靠的

情绪花园轮询后端拿分析结果，原来是「值变了 = 算完了」。
但**「没完成」也有默认值（中性/50），「完成」也可能恰好等于默认值**。
唯一可靠的做法：让产出方**显式标记状态**（`analyzed: true/false`）。

### ⑤ 返回 `-1` 而不是 `0`

`0` = 「真的没人」，`-1` = 「我不知道」。
混成一个值，**监控就会在最需要它的时候撒谎** —— 真出事时看板一片绿，比没有看板更糟。

### ⑥ 「没传」和「传错了」必须区别对待

`switch` 的 `default: throw` 是个陷阱：
`if/else` 里最后那个 `else` 不写就什么都不做，空串天然安全；
一旦改成 `switch` + `default: throw`，**空串从「无害」变成「致命」**。
前端列表页不传 `sortField` → 空串 → 落到 `default` → 整个页面报错。

### ⑦ 「登录」不等于「有权」

这是踩过两次的坑（日记 IDOR、看板越权）。
判断标准不是「他有没有 token」，而是「这个数据该不该给他看」。
同一个系统里，「C 端能登录」和「C 端能看全站数据」是两件事。

### 必须秒答（10 问）

| # | 问题 | 一句话答法 |
|---|---|---|
| 1 | 你用了哪些数据结构？ | String / Set / ZSet / **Bitmap** / HyperLogLog / Stream。**没有 List 和 Hash —— 因为没场景需要** |
| 2 | 为什么用 HLL 不用 Set？ | 内存跟人数成正比 vs 固定 12KB。UV 是看趋势的指标，0.81% 误差可接受 |
| 3 | ZSet 和 Set 的区别？ | Set 无序去重，只能答「在不在」；ZSet 每个 member 带 score，能按分数范围过滤和排序 |
| 4 | 缓存穿透 / 击穿 / 雪崩的区别？ | 穿透=查不存在的数据；击穿=热点 key 过期瞬间并发回源；雪崩=大量 key 同时过期 |
| 5 | 你解决穿透了吗？ | 解决了，用**墓碑 key** 记住「查过、结果是 0」，防的是空结果反复回源 |
| 6 | 缓存和数据库怎么保持一致？ | 写路径 `@CacheEvict` 删缓存，读路径 `@Cacheable` 重建。不依赖 TTL |
| 7 | Stream 和 List 做队列的区别？ | List 取走即消失；Stream 取走要签收，失败能重投 |
| 8 | PEL 是什么？ | Pending Entries List，不是消息副本，是「谁拿走了、多久没确认」的索引 |
| 9 | `XACK` 会删消息吗？ | **不会**。只是把消息从 PEL 里划掉，`XLEN` 不变 |
| 10 | 分布式锁怎么实现的？ | `SET key value NX PX 30000`，value 用 UUID 防误删，释放时校验 value |

### 可以想一想（15 问）

| # | 问题 | 答法要点 |
|---|---|---|
| 11 | HLL 原理是什么？ | 基于「观测到的最大前导零位数」估算基数。误差率约 `1.04/√m`，`m=16384` 时约 0.81% |
| 12 | HLL 能删除元素吗？ | **不能**。所以它只适合「只增不减」的统计（UV），不适合「在线人数」 |
| 13 | 为什么在线人数必须用 ZSet？ | 要按时间窗口过滤「谁还在」，HLL 答不了 |
| 14 | ZSet 底层结构？ | 元素少时用 ziplist/listpack，超过阈值转 skiplist + dict。**dict 保证 O(1) 查分数，skiplist 保证 O(logN) 范围查询** |
| 15 | 天级 key 会不会太多？ | 8 天 TTL 自动过期，峰值 8 个 key + 1 个合并 key |
| 16 | `ZUNIONSTORE` 的复杂度？ | `O(N)+O(M log M)`，N 是总元素数、M 是结果集大小。7 天数据量下毫秒级 |
| 17 | 死信队列怎么处理的？ | 重试 ≥3 次 `XADD` 到 `stream:ai:task:dead` 然后 `XACK`，人工排查 |
| 18 | 为什么 `analyze()` 返回 boolean？ | `void` 只能「调完就 ACK」，失败也签收，PEL 成摆设。返回 boolean 才有「真成功」这个信号 |
| 19 | `XAUTOCLAIM` 为什么不用？ | **Spring Data Redis 3.5 没有**，只能 `XPENDING` + `XCLAIM` 两步走 |
| 20 | 缓存击穿怎么防？ | `@Cacheable(sync=true)` 能挡，但它和 `unless` 冲突。**当前并发量下不值得改** |
| 21 | 为什么不做缓存预热？ | 分类树懒加载，第一个请求查库 + 拼树。当前数据量下收益 **< 100ms**，不值得增加启动复杂度 |
| 22 | 限流为什么用滑动窗口？ | 固定窗口有临界问题：59 秒打满 5 次、61 秒又能打 5 次，2 秒内实际放行 10 次 |
| 23 | 秒传的 md5 碰撞怎么办？ | 理论存在实际极低。在意就换 SHA-256，或 md5 + size 双条件 |
| 24 | 秒传跨用户越权？ | A 传过的文件 B 能秒传到同一个 objectKey。本项目 OSS 是公开直链可接受；**私密文件必须校验权限，不能只认 md5** |
| 25 | 秒传写库失败能删 OSS 文件吗？ | **命中缓存时不能删** —— 那个 objectKey 是别人上传时创建的，可能被 N 条记录引用，删了会搞挂别人的记录 |

## 7. 主动暴露的三个不足（显得诚实且有判断力）

> 面试官问「这个项目有什么不足」时，不要答「没什么不足」或「代码写得不够优雅」。
> 要答**具体的、你权衡过的、有明确理由不做的**。

### 不足一：缓存预热没做

分类树是懒加载，第一个请求要查库 + 拼树。可以加 `ApplicationRunner` 启动时预热，
但**当前数据量下收益 < 100ms**，增加启动复杂度和「预热失败怎么办」的处理成本，不值得。

> 潜台词：我知道这个优化点存在，我算过收益，我选择不做。

### 不足二：缓存击穿没处理

热点文章过期瞬间会并发回源。`@Cacheable(sync=true)` 能挡，
但它和 `unless` 冲突（`unless` 用来「不缓存 null 结果」，`sync` 加锁后拿不到返回值）。
当前并发量下不值得为此重构。

> 潜台词：我知道正确解法，也知道它的代价，我判断现在不该付。

### 不足三：会话列表捞全量消息

`KnowledgeConsultationService` 里用 `in(sessionIds)` 把一页所有会话的**全部消息**捞出来，
只为了算条数和取最后一条。一个会话 500 条、一页 10 个，就是 5000 行。
**正解是 SQL 聚合（`COUNT(*)` + `MAX(created_at)`），或者把 `messageCount` / `lastMessage` 冗余到 session 表 —— 不是加缓存。**
缓存只会让这个错误的查询跑得"更快"，不会让它变对。

> 潜台词：**我能分清「性能问题」和「设计问题」。加缓存解决不了设计问题。**

## 8. 面试前 5 分钟速记卡

```
13 个场景 / 5 种结构（String Set ZSet HLL Stream，无 List 无 Hash）
5 类问题：省库 · 省内存 · 跨请求状态 · 跨进程通信 · 排序

三个必须讲的坑：
  1. UV 的 0 是二义的 → EXISTS + 墓碑 key
  2. 空 HLL 造不出来 → Spring 和 Lettuce 各一道 notEmpty
  3. 滚动升级旧实例吃掉新类型消息 → 必须停旧起新

三个数字：
  0.81%      HLL 实测误差
  360KB      HLL 内存（30 天）
  60 秒      看板 TTL（vs 用户信息 30 分钟）

三句最能加分的话：
  "我不是见到缓存就加，而是先判断这个问题属于哪一类。"
  "返回 -1 而不是 0 —— 0 是'真的没人'，-1 是'我不知道'。"
  "加缓存解决不了设计问题，只会让错误的查询跑得更快。"

三个主动说的不足：
  缓存预热（收益 < 100ms）· 缓存击穿（sync 与 unless 冲突）· 会话列表捞全量（该改 SQL 不该加缓存）
```

**两份怎么串起来讲**（这段建议背下来）：

> 一开始所有状态都放 JVM 内存——会话记忆放 `ConcurrentHashMap`、任务队列用 `@Async`。
> 后来发现三个问题：重启就丢、多实例串不上、任务失败了没人知道。
> 所以我做了一轮改造：**能放 Redis 的状态全挪出去**，
> **留在进程内的只有真正的并发控制**（线程池、原子标记、本地锁）。
>
> 边界是这么划的：**需要跨请求、跨实例、跨重启的状态，都归 Redis；
> 只是「这一段代码同时只能有一个人跑」的，归本地锁。**
> 本地锁能做的不要上分布式锁——多一次网络往返，还多一个故障点。
