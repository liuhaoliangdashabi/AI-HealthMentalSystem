### Step 2　处置 UV 回源（唯一需要决策的地方）

`queryUvDetailFromDb` 存在的意义：某天 `uv:{day}` 不存在时，回库捞 user_id 补算。两个选择：

**A. 推荐：删掉回源，Redis 没有就按 0**

- 依据：diary / consult **写入时**就已经 `PFADD uv:{day}`，而 `RedisKeys.uv(day)` 在两边是**同一个 key**，所以 30 天活跃 = `PFCOUNT` 多 key 并集，天然跨服务去重
- 回源是迁移期补丁，而且它读的正是要拆掉的两个别人的库
- 代价：Redis 接入之前的历史日期会显示 0（看板上那几天的曲线缺一段）
- 想要历史：写个**一次性**回填脚本（读两个库 → PFADD → 跑完删掉），别把它留在请求路径里

**B. 保历史：各服务开回源接口**

diary / consult 各加 `/internal/{svc}/uv/fallback?days=30` 返回 `Map<date, List<userId>>`，analytics 合并。
缺点：几十万 ID 跨进程传输——这正是我们刚刚否掉的方案，不建议回头。
