## 一、为什么要做这个练习

项目里所有写操作到现在都是**单表一条 SQL**：

```
新增文章   →  INSERT knowledge_article          （1 条）
修改文章   →  UPDATE knowledge_article          （1 条）
改状态     →  UPDATE knowledge_article          （1 条）
上传文件   →  INSERT sys_file_info              （1 条）
```

**单条 SQL 本身就是原子的，数据库自动保证"要么成功要么失败"，根本用不上事务。**

所以整个项目到现在一个 `@Transactional` 都没写过 —— 这不是漏了，是确实没场景。

**这个练习是为了造出第一个"多表写入"的场景。**

---

## 二、业务规则

```
DELETE /api/knowledge/category/{id}

① 不允许删"默认分类"（id = 1）—— 不然文章没地方挪
② 把这个分类下的文章，全部挪到默认分类
③ 删掉这个分类
```

**② 和 ③ 必须在一个事务里。**

---

## 三、为什么这里必须用事务

### 原因 1：两步写入，不能只成功一半

```
如果 ② 成功、③ 失败：
   → 文章全被挪到了默认分类
   → 但这个分类还在
   → 用户看到一个【空分类】，以为删失败了，但其实文章已经被挪走了
   → 数据处在【中间状态】
```

### 原因 2：外键逼你必须有顺序

```sql
CONSTRAINT `knowledge_article_ibfk_1`
  FOREIGN KEY (`category_id`) REFERENCES `knowledge_category` (`id`)
  ON DELETE RESTRICT
```

`RESTRICT` 的意思是：**分类下还有文章时，禁止删除这个分类。**

```
所以顺序必须是：
   先挪文章（把引用解除）
   再删分类

如果反着来 → 数据库直接报外键错误
```

**这也是"为什么不能只写一条 DELETE"的原因。**

## 四、完整代码

### 4.1 `KnowledgeCategoryService`

**先加一个注入：**

```java
private final KnowledgeCategoryMapper categoryMapper;
private final KnowledgeArticleMapper articleMapper;   // ← 新增

public KnowledgeCategoryService(KnowledgeCategoryMapper categoryMapper,
                                KnowledgeArticleMapper articleMapper) {
    this.categoryMapper = categoryMapper;
    this.articleMapper = articleMapper;
}
```

> 跨模块直接注入 Mapper 是正常的。只有真正需要**复用业务逻辑**时才注入对方的 Service。

**再加方法（第一遍先不加 `@Transactional`）：**

```java
//默认分类 id（"心理健康基础"）—— 文章都往这挪
private static final Long DEFAULT_CATEGORY_ID = 1L;

public void deleteCategory(Long categoryId) {
    //① 不允许删默认分类
    if (DEFAULT_CATEGORY_ID.equals(categoryId)) {
        throw new BusinessException("默认分类不能删除");
    }

    //② 校验分类存在
    KnowledgeCategory category = categoryMapper.selectById(categoryId);
    if (category == null) {
        throw new BusinessException("分类不存在");
    }

    //③ 把这个分类下的文章挪到默认分类
    int moved = articleMapper.update(null,
            new LambdaUpdateWrapper<KnowledgeArticle>()
                    .eq(KnowledgeArticle::getCategoryId, categoryId)
                    .set(KnowledgeArticle::getCategoryId, DEFAULT_CATEGORY_ID));

    //④ 删掉这个分类
    categoryMapper.deleteById(categoryId);

    log.info("删除分类成功：id={}，挪走了 {} 篇文章", categoryId, moved);
}
```

**需要补的 import：**

```java
import com.baomidou.mybatisplus.core.conditions.update.LambdaUpdateWrapper;
import org.example.aispringboot.entity.KnowledgeArticle;
import org.example.aispringboot.mapper.KnowledgeArticleMapper;
import org.example.common.BusinessException;
```

**类上要有 `@Slf4j`。**

### 4.2 `KnowledgeController`

```java
@DeleteMapping("/knowledge/category/{id}")
public Result<Void> deleteCategory(@PathVariable Long id){
    log.debug("删除分类：{}", id);
    categoryService.deleteCategory(id);
    return Result.success();
}
```

> ⚠️ 前端 `knowledge.vue` 没有这个功能（它只读分类树）。这个接口是为了练事务自己造的，用 curl / APIFox 测。

## 五、四步验证流程（核心）

### 第 1 步 · 先不加事务，正常跑通

按上面代码写完（**不加 `@Transactional`**），编译、重启。

```bash
curl -X DELETE http://localhost:8080/api/knowledge/category/2 -H "token: 你的token"
```

**用分类 2（情绪管理）测** —— 它下面有文章。分类 4（人际关系）下面没有文章，测不出效果。

**去 Navicat 查：**

```sql
SELECT id, title, category_id FROM knowledge_article WHERE category_id = 1;
-- 应该看到原本属于分类 2 的文章，现在 category_id 变成了 1

SELECT * FROM knowledge_category WHERE id = 2;
-- 分类 2 没了
```

**正常成功 ✓**

### 第 2 步 · 人为制造异常，**不加事务**跑一次 ⭐

**先把数据恢复**（把刚才挪走的文章改回分类 2）：

```sql
-- 先查出来是哪些
SELECT id, title FROM knowledge_article WHERE category_id = 1;
-- 然后手动改回去（按你知道的那几条的 id）
UPDATE knowledge_article SET category_id = 2 WHERE id IN (...);
```

**然后在 ③ 和 ④ 之间插一行：**

```java
    //③ 挪文章
    int moved = articleMapper.update(...);

    // ★★★ 临时加这一行 ★★★
    if (true) throw new RuntimeException("人为制造的异常");

    //④ 删分类
    categoryMapper.deleteById(categoryId);
```

**重启，再打一次同样的 curl，然后查库：**

```sql
SELECT id, title, category_id FROM knowledge_article WHERE category_id = 2;
-- 【空了】← 文章被挪走了

SELECT * FROM knowledge_category WHERE id = 2;
-- 【还在】← 分类没删掉
```

**★ 这就是"没有事务"的后果：一半成功、一半失败，数据处在中间状态。**

**接口报 500，但数据库已经被改坏了一半。**

### 第 3 步 · 加上 `@Transactional`，再跑一次 ⭐

**先把数据恢复**，然后：

```java
@Transactional                       // ← 加这一行
public void deleteCategory(Long categoryId) {
```

**重启，再打一次同样的 curl（那行 `if (true) throw` 还在），然后查库：**

```sql
SELECT id, title, category_id FROM knowledge_article WHERE category_id = 2;
-- 【还在原位】← 没有被挪走！

SELECT * FROM knowledge_category WHERE id = 2;
-- 【还在】
```

**★ 事务回滚了 —— 第 ③ 步的操作被撤销了。**

**接口还是报 500，但数据库【纹丝不动】。**

### 第 4 步 · 删掉那行人为异常，正常跑

```java
    //③ 挪文章
    int moved = articleMapper.update(...);

    //（那行 if (true) throw 删掉）

    //④ 删分类
    categoryMapper.deleteById(categoryId);
```

**再打一次 → 文章挪到 1、分类 2 消失 → 业务成功 ✓**

---

### 第 2 步 vs 第 3 步 —— 这就是你要练的东西

```
不加 @Transactional：  挪走的文章【回不来】
加了 @Transactional：  挪走的文章【回来了】
```

**亲眼看到差别，就永远不会忘"事务是干什么用的"。**

## 六、`@Transactional` 生效的四个前提

```
① 类是 Spring Bean              @Service ✓
② 方法是 public                 ✓
③ 从【外部】调用                 Controller → Service ✓
   ⚠️ 如果 Service 内部 this.xxx() 调用自己另一个方法，事务【不生效】
④ 抛的是 RuntimeException 才回滚
```

**第 ④ 条最容易被忽略，去确认一下：**

```java
public class BusinessException extends RuntimeException { ... }
//                                        ↑ 必须是 RuntimeException
```

**如果是 `extends Exception`，第 3 步会看到"回滚没生效"，然后你会怀疑 `@Transactional` 写错了 —— 实际是异常类型的问题。**

**要么改继承，要么写 `@Transactional(rollbackFor = Exception.class)`。**

## 七、附录：事务面试常考知识点

### 7.1 `@Transactional` 失效的 7 种场景 ⭐ 最高频

```
① 方法不是 public
   → Spring AOP 只代理 public 方法，private/protected 上的注解直接无视

② 同类内部调用                        ← 考得最多
   this.otherMethod();   // 不走代理，直接调原始对象 → 事务不生效
   解决：拆到另一个 Bean / 注入自己 / AopContext.currentProxy()

③ 异常被自己 catch 了
   try { ... } catch(Exception e) { log.error(...); }
   → 没抛出去，Spring 不知道要回滚

④ 抛的是 checked 异常
   → 默认 rollbackFor = RuntimeException.class
   → 要回滚 checked 得写 @Transactional(rollbackFor = Exception.class)

⑤ 数据库引擎不支持
   → MyISAM 不支持事务（InnoDB 支持）

⑥ 传播行为设成了 NOT_SUPPORTED / NEVER

⑦ 这个类不是 Spring 管的
   → 自己 new 出来的对象，没有代理
```

**② 和 `@Async` 的同类调用失效是【同一个原理】—— 都靠动态代理，`this` 指向的是原始对象，不是代理。**

### 7.2 传播行为（第二高频）

```
REQUIRED（默认）   有事务就加入，没有就开一个
REQUIRES_NEW       不管有没有，都开一个新的（把当前的挂起）
NESTED             嵌套，用 savepoint，可以局部回滚
SUPPORTS           有就用，没有就算了
NOT_SUPPORTED      挂起当前，非事务执行
MANDATORY          必须有事务，没有就抛异常
NEVER              必须没有事务，有就抛异常
```

**最常问 REQUIRED vs REQUIRES_NEW：**

```
REQUIRED       →  共用同一个事务，一个回滚全回滚
REQUIRES_NEW   →  各管各的，外层回滚了内层照样提交

经典用例：记操作日志
   主业务失败要回滚，但"失败日志"必须留下来
   → 日志方法用 REQUIRES_NEW
```

### 7.3 隔离级别 + 三种读问题

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|:---:|:---:|:---:|
| READ UNCOMMITTED | ✗ | ✗ | ✗ |
| READ COMMITTED | ✓ | ✗ | ✗ |
| **REPEATABLE READ** | ✓ | ✓ | ✗ |
| SERIALIZABLE | ✓ | ✓ | ✓ |

```
MySQL 默认 REPEATABLE READ
Oracle 默认 READ COMMITTED
```

```
脏读       ：读到了别人【还没提交】的数据，人家一回滚，你读的就是假的
不可重复读 ：同一个事务里读两次，结果不一样（别人 UPDATE 并提交了）
幻读       ：同一个事务里查两次，第二次多出几行（别人 INSERT 并提交了）
```

### 7.4 长事务的危害

```
① 占用数据库连接 → 连接池耗尽 → 全站排队
② 锁持有时间长 → 阻塞其他事务
③ undo log 不能清理 → 回滚段膨胀
④ 主从延迟 → binlog 要等事务提交才写，从库追不上
```

**结论：不要在事务里做网络调用、不要做耗时计算、不要等用户输入。**

> 上传文件那个场景之所以"先传 OSS 再写表"（而不是塞进事务），就是因为事务里做 HTTP 调用 = 长事务。

### 7.5 分布式事务（知道思路即可）

```
2PC（两阶段提交）  准备阶段 + 提交阶段。强一致，但阻塞、性能差
TCC               Try-Confirm-Cancel，业务层面实现，侵入大
Saga              拆成一串本地事务 + 补偿操作
本地消息表         把"要发的消息"和业务数据写进同一个本地事务
最大努力通知       一直重试，直到成功
```

**关键认知：事务管的是"一个数据库连接上的一组操作"。跨 HTTP / 文件系统 / MQ 的那一步永远在事务之外，只能靠【补偿】。**

### 8.1 测完记得恢复数据

```
用分类 2 或 3 测，文章会被挪到分类 1
测完手动改回来：
    UPDATE knowledge_article SET category_id = 2 WHERE id IN (...);

```

### 8.2 检查清单

```
□ KnowledgeCategoryService 注入了 KnowledgeArticleMapper
□ BusinessException extends RuntimeException
□ 方法签名是 public
□ Controller 调用（不是 Service 内部自调）
□ 第 2 步看到了"文章被挪走但分类还在"
□ 第 3 步看到了"什么都没变"
□ 第 4 步正常成功
```

### 8.3 这个接口前端用不上

前端 `knowledge.vue` 只读分类树。这个接口是为了练事务造的，以后做"分类管理"页面时能直接复用。
